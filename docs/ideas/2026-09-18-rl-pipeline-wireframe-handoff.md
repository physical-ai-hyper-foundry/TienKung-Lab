- **폰트**: `.dl` 은 Pretendard 를 쓰는데, 아티팩트는 Google Fonts 외의 스타일시트를 막는다(앱은 `index.html` 에서 jsdelivr 로 받는다). 그래서 이 문서가 실제로 쓰는 글자만 남긴 **가변 서브셋 woff2 를 base64 로 인라인**해 두었다(623 글리프 / 129KB). 본문에 새 한글을 많이 넣으면 서브셋을 다시 떠야 한다 — `pyftsubset` 으로 `~/Library/Fonts/PretendardVariable.ttf` 를 `--text-file` 로 자르고 `@font-face` 의 base64 를 갈아 끼운다.

  - **Unitree G1 은 없다.** 와이어프레임 두 곳(⓪-b · ⓪-c)에 지원 로봇으로 적어 뒀던 것을 지웠다. `assets/tienkung2_lite/tienkung.py:19,23` 에 *"Configuration for Unitree robots"* · `G1_MINIMAL_CFG` 가 보이는데 **Isaac Lab 원본에서 복사된 docstring 잔재**고 파일 내용은 TienKung 설정이다.
  - 따라서 ① 학습 요청의 태스크 후보는 고른 로봇에 따라 **4개(TienKung) 또는 1개(X2)** 다.
- 태스크는 사용자가 만드는 게 아니라 우리가 로봇별로 코드 배포하는 지원 목록. 지원 태스크가 없는 로봇이면 강화학습 체크 자체가 비활성(이 검사는 로봇만 있으면 되므로 태스크 선택과 무관).
- 강화학습만 고른 작업은 원본·학습 데이터 메뉴를 숨긴다.
- 왼쪽 스테퍼(세로 단계 목록)는 **뺐다 — 2026-09-18 제거 확정**(보류 아님). 구현 시 `TaskFormSidebar.tsx` 와 `TaskForm.tsx` 의 `activeStep` · `sectionRefs` · `isSectionFilled` · `scrollToSection` 이 같이 사라진다.
- DB: `tasks` 의 모방 전용 컬럼(collection_environment, result_labels, instructions, source_types)은 nullable 로 바꿔야 한다.

### ⓪-d 작업 수정 (`/library/projects/{projectId}/tasks/{taskId}/edit`) — 무엇을 잠그나 (2026-09-22 결정, 사용자 발의)

> 사용자 지적: *"작업 생성할 때 우리가 모방/강화를 받고 있는데 작업 수정할 때에는? 이걸 또 건드리는 게 말이 되나? 로봇은 진짜 수정하면 좀 그래."*

**지금은 전부 수정 가능하다.** `TaskUpdateCommand` 는 `TaskCreateCommand` 에서 `projectId` 만 뺀 것이고, 화면도 같은 폼을 재사용한다(`EditTaskPage.tsx` → `TaskForm mode="edit"`; `mode` 는 제목·버튼 문구만 바꾼다, `TaskForm.tsx:196,198,205`). 가드는 **수집 경로 하나뿐**이다(`TaskService.kt:117-120`, `SOURCE_TYPE_IN_USE` 409).

**근거는 코드에 이미 적혀 있다.**
- `V4__create_tasks_and_catalog.sql:74-76` — *"이미 dataset이 쓰는 선택을 task에서 빼면 FK가 막아준다(**조용한 불일치 방지**)"*
- `RobotService.kt:63` — *"삭제 — 작업/에피소드가 참조 중인 로봇은 막는다(409). **이력 보존을 위해** 참조를 먼저 정리해야 한다"*
- **비대칭이 문제다**: 로봇을 *지우는* 건 막혀 있는데 작업에서 *갈아끼우는* 건 무방비다. 그리고 갈아끼우기가 더 나쁘다 — 삭제는 409로 막히고 끝이지만, 갈아끼우면 과거 에피소드·학습이 **조용히 다른 로봇 것으로 표시된다**(`training_runs` 에 로봇 스냅샷이 없어 알아챌 방법도 없다).

**규칙 하나로 쓴다 — "하위가 쓰고 있으면 못 바꾼다."**

| 필드 | 수정 | 근거 |
|---|---|---|
| 이름 · 설명 · 수집 환경 · 대표 이미지 | **항상 가능** | 표시용. 깨질 게 없다 |
| 작업 유형 | **항상 가능** | 분류일 뿐. 탐색 집계가 옮겨갈 뿐 데이터는 안 깨진다 |
| 수집 경로(소스 타입) | **쓰이는 것만 잠금 · 추가는 자유** | 현행 유지(`SOURCE_TYPE_IN_USE`) |
| 수집 결과 라벨 · 지시문 | **잠그지 않는다** (아래) | 에피소드가 스냅샷을 들고 있고 필터 후보도 데이터에서 뽑는다 |
| **로봇** | **하위 데이터가 하나라도 있으면 잠금** | 에피소드·학습이 그 로봇으로 만들어졌다. 단일 값이라 "추가" 개념이 없다 |
| **학습 유형(모방/강화)** | **수정 불가 — 추가도 안 된다** | 잠금 두 개가 얽힌다. 아래 |

**라벨 · 지시문에는 가드가 필요 없다 (2026-09-22 확인).** 한때 "기존 구멍" 이라고 적었는데 **틀렸다** — 설계가 이미 피해 놨다.
- `V6__create_episodes.sql:15-17` — `selected_instruction` · `outcome_result` · `outcome_reason` 은 전부 **문자열 스냅샷**이고 FK 가 없다. 주석: *"선택한 지시문 스냅샷 (**task 목록과 대조 검증 안 함**)"*.
- 필터 후보도 **실제 데이터에서 뽑는다** — `EpisodeReader.countGroupedByOutcomeResult` · `groupBy(SELECTED_INSTRUCTION)`. FE 주석이 명시한다(`useEpisodeSummary.ts:4-6`, `SourceDataDetailPage.tsx:137-139`): *"not task.resultLabels — which is just the task's configured label set and **may not match what's actually been collected**"*.
- `task.resultLabels` 는 **색 조회용**으로만 쓰인다(`EpisodeService.kt:164`, `colorByLabel[label]`).
- 그래서 **지워도 필터·집계는 멀쩡하고 색만 잃는다.** 대신 **이름을 바꾸면 집계가 둘로 쪼개진다**(옛 이름 에피소드 + 새 이름 에피소드). 이건 잠금이 아니라 **저장 전 경고 한 줄**로 처리한다 — 잠그면 오타를 영영 못 고친다.

**학습 유형은 수정에서 통째로 뺀다 (2026-09-22, 사용자 결정).** 한때 "쓰이는 것만 잠그고 추가는 자유" 로 잡았다가 철회했다.
- **철회 이유 — 잠금 두 개가 얽힌다.** 모방학습 작업에 `+ 강화학습` 을 하려면 그 작업의 **로봇이 강화학습 지원 목록에 있어야** 하는데, 데이터가 있는 작업은 **로봇도 이미 잠겨 있다.** 지원 안 되는 로봇이면 **풀 방법이 없는 막다른 길**이 된다. 게다가 나중에 지원 목록이 늘면 같은 작업의 버튼이 어느 날 갑자기 살아나는데, 화면으로 설명할 수 없다. 사용자: *"그냥 작업 수정의 경우 학습 유형은 못 바꾸게 하자. 복잡해진다. 강화학습에서 모방학습 추가는 상관이 없는데, 모방학습에서 강화학습을 추가할 경우 지원되지 않은 로봇일 때 복잡해진다."*
- **반대 방향(강화 → 모방 추가)은 막힐 이유가 없지만 같이 뺀다.** 한쪽만 되는 규칙은 설명이 길어진다 — **규칙 하나가 예외 둘보다 싸다.**
- **데이터가 없어도 못 바꾼다.** 빈 작업이면 지우고 다시 만드는 비용이 거의 없다.
- **치르는 값**: "모방으로 시작했는데 강화도 해보자" 면 **작업을 새로 만들어야 하고, 같은 로봇 · 같은 현장인데 작업이 둘로 쪼개진다.** 다만 강화학습 작업은 에피소드가 없어 새로 만드는 비용이 거의 0이고(이름 · 유형 · 설명 · 로봇뿐), 두 방식은 실제로 다른 것을 한다(모방 = 조작, 강화 = 보행 · 균형)라 작업이 갈리는 게 부자연스럽지도 않다.
- **구현**: `TaskUpdateCommand` 에 학습 유형 필드를 **아예 넣지 않는다** — 필드가 없으면 가드도 필요 없다.

**진입점과 삭제는 이미 구현되어 있다 (2026-09-23 코드 확인).** `TaskSettingsPage.tsx` 가 **작업 설정** 화면이고 우상단에 `작업 수정` 버튼(`NeutralButton` + `FormOutlined` → `/tasks/{taskId}/edit`), 맨 아래에 **삭제 위험 구역**(`DeleteZone.tsx` → `DangerZone.tsx`, 빨간 카드 + 확인 모달)이 있다. 프로젝트 설정(`SettingsPage.tsx`)·원본 데이터 설정(`SourceDataSettingsPage.tsx`)도 같은 구조다. **3차에 더해지는 것은 설정 화면의 "학습 유형" 행 하나.** 와이어프레임 ⓪-d 첫 프레임이 이 화면이다.

**화면은 한 장이다 — 단계를 밟지 않는다.** 생성은 2단계지만 수정은 아니다: 수정은 정해진 작업의 **한 칸을 고치러** 오는 자리이고, 우리 규칙상 학습 유형은 거의 못 바꾸는 값이라 단계로 물어도 되돌아올 답이 없다. 사용자 지적: *"이러면 작업 수정할 때 학습 유형은 거의 안 바꾸겠다! 라고 하는 거나 마찬가지인데."* — 맞다. 그게 바로 위 규칙이다.


**체크박스도 사라졌다.** 잠긴 체크박스는 **기표가 어긋난다** — 체크박스는 *"끌 수 있다"* 는 약속이고 자물쇠는 *"못 끈다"* 는 말이라 한 칸 안에서 부딪친다. 이제는 **값 한 줄**이다:

```
학습 유형
모방학습 🔒
학습 유형은 작업을 만들 때 정해지고 수정할 수 없습니다. 다른 방식이 필요하면 새 작업을 만드세요.
```

**할 수 있는 일만 화면에 있고, 못 하는 일은 애초에 조작 요소가 아니다.**

**두 번째 프레임(⓪-d -b)은 "데이터가 아직 없는 작업"** 이다 — 로봇과 소스 타입이 열리고, 학습 유형만 그때도 잠겨 있다.

**화면**: 잠긴 항목은 **숨기지 말고 비활성화 + 이유**. 숨기면 "원래 없는 값" 으로 읽히고 비활성화하면 "바꿀 수 없는 값" 으로 읽힌다. ② 배너가 이미 같은 어법을 쓴다(*"로봇 · 태스크 · 출력 경로는 여기서 바꿀 수 없습니다"*).

**구현 시 손댈 곳**: `TaskService.update` 에 로봇 · 학습 유형 가드 추가(에러 코드 신설 — `ROBOT_IN_USE` 는 카탈로그 삭제용이라 재사용하지 않는 편이 낫다), `TaskForm` 에 `mode === "edit"` 분기(지금은 제목·버튼 문구만 바꾼다), 잠금 사유를 주는 API 필드.

### ⓪-b 작업 목록 (`/library/projects/{projectId}/tasks`, `TaskSection.tsx`, `TaskCard.tsx`)
- 프로젝트 단계는 펼친 앱 사이드바(272px: 로고, 프로젝트 카드, 작업/데이터 탐색/설정)만 있다. 아이콘 레일+서브메뉴는 작업 안에서만.
- 카드의 작업 유형 태그 옆에 학습 유형을 **태그가 아니라 보조 텍스트**로 단다(2026-09-18 결정, E 안). 제조사·로봇명과 같은 톤의 12px 회색 텍스트 — `모방학습 · 강화학습`.
  - 왜: 태그를 하나 더 늘리면 한 줄에 태그가 셋이 되고, 작업 유형 태그(14px/600 geekblue)와 크기가 달라 위계가 사라진다. 모방학습에 파랑을 쓰면 작업 유형 태그와 같은 geekblue 계열이라 분류인지 속성인지 구분이 안 되고, 강화학습에 초록을 쓰면 antd 의 "성공" 색과 의미가 충돌한다. **분류는 태그, 속성은 텍스트**로 가른다.
  - 검토했다가 뺀 안(⓪-b-2 에 A·B·E 만 남겨 둠): **제목 옆 아이콘** — 처음 보면 뜻을 모른다. **개수 줄에 통합**(`학습 5개` → `모방학습 3개 · 강화학습 2개`) — "강화학습이든 모방학습이든 어쨌든 학습인데 정보만 많아진다"(사용자).
- 강화학습 전용 카드는 원본·에피소드·학습 데이터 개수를 빼고 학습 개수만. 클릭 시 원본 데이터 관리가 아니라 학습 관리로 진입.

### ⓪-c 강화학습 전용 작업 진입 (`TaskSubMenu.tsx`)
- 서브메뉴에서 원본 데이터·학습 데이터 그룹이 빠지고 학습(학습 요청, 학습 관리)과 설정만.
- 기본 화면은 **학습 관리**(원본 데이터 관리가 "가진 것의 목록" 이듯). 학습이 없으면 학습 요청으로 가는 빈 카드.

### ① 학습 요청 (`/library/tasks/{taskId}/trainings/request`)
- 로봇은 작업에 묶여 있으니 고르지 않는다. 학습 유형(모방/강화, ⓪ 에서 고른 방식만) + 강화학습 태스크. **태스크를 고르는 유일한 자리다** — 후보는 작업 로봇에 지원되는 태스크 전부이고 작업이 좁히지 않는다.
- 오른쪽 요약: 로봇 모델(작업 설정에서 지정됨), 태스크, 자유도, 시뮬 에셋, 지원 시뮬레이터. 시뮬레이션 환경은 Model Studio 에서 고른다.

### ② Model Studio 강화학습 설정 (새 탭)
- 사이드바는 "학습 파이프라인 생성" 대신 **모방학습 / 강화학습** 두 항목(아이콘: 실린더 / 과녁). 모방학습 페이지 버튼도 "학습 요청".
- 왼쪽: 기본 설정(로봇·태스크 읽기 전용) → **시뮬레이션 환경** 3택: "Isaac Sim (PhysX) / Isaac Sim (Newton) / MuJoCo(준비 중)", 각 카드에 시뮬레이터 → 물리 프레임워크 → 솔버 세 층 표기 → 런 이름·출력 디렉토리 → 강화학습 파라미터(Headless 토글, 병렬 환경 4096, 최대 iteration 50000, 체크포인트 간격 **1000**, Seed, "중간 체크포인트도 모델로 등록" 토글 기본 꺼짐, Config 미리보기 버튼(이모지 없음)).
- 오른쪽: 보상 함수 카드(항목마다 ? 호버 툴팁, 값의 방향이 무엇을 바꾸는지 설명) + 환경 난이도 + "학습 요청" 버튼.
- 뺀 것: 실행 커맨드 미리보기, 실행 위치 섹션(MLXP 종료 예정, 로컬만), Resume(D17: 이어서 학습 미제공).

### ③ 학습 실행 현황 (`/model-studio/runs`)
- 필터는 **멀티셀렉트 드롭다운 3개**(학습 유형 · 파이프라인 · 상태) + 런 이름 검색. 칩 나열은 사용자가 "더럽다" 고 거부.

  - **결론**: 플레이어 **640px 고정**, 오른쪽은 **빈 채로 둔다** — 였다가 **같은 날 늦게 실행 조건이 들어와 채워졌다**(아래). 빈 칸을 먼저 만들어 두고 **진짜 들어갈 것이 생겼을 때** 채운 순서다. 아래에 회색 한 줄만 — *"학습 화면이 아니라 평지에서 외란(노이즈·외력) 없이 따로 찍은 영상입니다."* "안 적으면 오해한다" 에 실제로 해당하는 건 이것 하나뿐이다. 전체 폭(1002px)으로 늘리지 않는 이유는 stage 가 564px 이 되어 학습 파라미터·로그를 스크롤 아래로 밀기 때문.

- **학습 파라미터를 둘로 갈랐다 (2026-09-22, 사용자 제안).** 한 표 안에 `실행` 그룹과 `기본값과 다르게 설정한 항목` 그룹이 같이 있었는데, 이건 **분류 축 두 개(무슨 파라미터인가 × 기본값에서 바꿨는가)를 한 축에 밀어 넣은 상태**였다 — 실행 파라미터를 하나라도 바꾸면 그 행이 두 그룹 중 어디로 가야 하는지 답이 없다. 축을 하나만 쓰기로 하고 바깥 축을 **종류**로 골랐다.

    - **폭 교정(2026-09-22)**: 처음엔 남은 폭을 전부 줬는데 **표가 플레이어와 맞먹어 보여 롤아웃이 작아 보였다.** 사용자 지적: *"실행조건을 저렇게 크게 줄 필요가 없지. 롤아웃이 너무 작아지잖아."* 실행 조건은 **영상의 캡션**이지 나란한 주인공이 아니다 → 300px 고정, 플레이어 640px 유지.
  - **학습 파라미터** = **보상 함수 + 환경 난이도** 11개. 칼럼은 `항목 / 설정 키 / 기본값 / 설정값` **4칸**. 기본은 **바뀐 2행 + `⌄ 기본값 그대로인 항목 9개 보기`**(접힘).
    - **항목을 한글·영문 두 칸으로 가른 이유(2026-09-22)**: `넘어짐 벌점 (termination_penalty)` 처럼 괄호로 붙이면 긴 이름에서 **줄바꿈 지점이 제멋대로**다. 칼럼을 나누면 영문 키가 세로로 줄이 맞아 훑기 쉽고, 바로 아래 **전체 학습 설정(env.yaml · agent.yaml)** 과 같은 키라서 **화면에서 본 키로 파일을 찾을 수 있다** → 이름도 `설정 키`.
  - **왜 종류가 바깥 축인가**: 두 묶음은 **읽는 목적도 표시 형식도 다르다**(재현용 값 = 키·값 목록 ↔ 정책 해석용 값 = 기본값 대비 표). 한 표에 있으면 이 규칙을 나눠 쓸 수 없다. 그리고 **② 설정 화면이 이미 그 축으로 갈라져 있다** — 왼쪽 열이 기본 설정 + 강화학습 파라미터(실행), 오른쪽 열이 보상 함수 + 환경 난이도. 설정과 상세가 같은 축으로 갈리면 "내가 만진 건 저기" 를 찾는 데 **지도가 하나만** 필요하다.
  - **왜 하필 롤아웃 옆인가**: HUD 가 이미 `iteration 50,000 · Isaac Sim (PhysX)` 를 말하고 있어 **HUD 가 실행 조건의 축약판**이 된다 — 붙여 두면 중복이 아니라 확대다. 다만 **제목은 따로 단다**(`학습 롤아웃` / `실행 조건`): 롤아웃 촬영 조건(평지 · 0.5 m/s · 10초)과 학습 실행 조건(4096 환경 · 50,000 iteration)은 다른 것이라 한 상자에 넣으면 **"롤아웃의 파라미터" 로 읽힌다.**
  - **실패·취소한 학습에는 롤아웃이 없다** → 그때는 실행 조건이 **폭 전체**를 쓴다. `params_artifact_id` 는 RUNNING 통보부터 채워지므로 실패해도 실행 조건은 있다(오히려 그때 제일 보고 싶은 값이다).
- **설정값이 기본값과 같으면 설정값 칸에 "기본값과 동일" (2026-09-22, 디자이너 제안 그대로).**
  - **한 번 잘못 읽었다.** 칼럼을 `항목 / 값` 둘로 합치고 기본값을 바뀐 행의 꼬리표로 내렸는데, 제안은 그게 아니었다. 사용자 정정: *"컬럼은 기본값 / 설정값 을 두되, 설정값이 기본값과 같다면 '기본값과 동일' 이라고 표시한다고 했던거다."* → **칼럼 3칸 유지**, 설정값 칸의 **중복 숫자만** 문구로.

    - **학습 상세의 첫 화면 주인공은 롤아웃**이고 파라미터는 그 아래다. 기본 = 바뀐 2행 + 토글.

  - 사용자: *"이 부분은 핵심이라기 보단 UI/UX 적인 성격이 크기 때문에 나는 크게 신경 안쓰고 있었다."* → **디자이너 판단 우선.**
- **막혀 있는 것 — 기본값이 DB 에 없다.** `training_runs.params_artifact_id` 가 가리키는 건 **이 학습이 쓴 값**이고 기본값은 학습 코드의 config 에 있다. 기본값은 **로봇·태스크마다 다르고 코드가 바뀌면 같이 바뀐다** — DL 이 화면을 그릴 때마다 코드를 읽어 비교하면 반년 뒤 같은 학습이 "기본값 그대로" 에서 "바꾼 항목" 으로 변한다. **MS 가 파라미터 아티팩트에 `{값, 기본값}` 쌍으로 넣어 보내야** 한다 — 계보를 스냅샷으로 굳힌 것과 같은 이유(`V36` 주석: *"학습 당시의 사실은 학습 당시에 박제한다"*). **이게 정해지기 전에는 위의 접기·꼬리표가 전부 못 그려진다 → MS 통보 스펙 변경 1건 추가.**

- **MS → DL 통보에 두 값을 더해야 한다 (2026-09-21).** 계보 카드가 쓰는 `{스텝수}스텝` 과 강화학습 `병렬 {N}개`(`num_envs`) 가 `training_runs` 에 칸이 없다. 둘 다 MS 가 아는 값이라 통보 계약을 늘리는 쪽이 맞다. 사용자: "ML 과 DL 이 통신할 때 추가로 줘야겠네. 불가능은 아니지."
- **계보는 이미 DB 에 있다.** `raw_dataset_name` 컬럼 주석이 문자 그대로 *"계보 카드의 원본 데이터"* 이고, `training_data_name` 과 함께 **학습 시점 스냅샷**이라 원본이 지워져도 표시가 남는다. 프로젝트명 · 작업명만 조인하면 네 단계가 완성된다. **빠진 건 목록 API 프로젝션**이다 — `TrainingRunSummary` 는 여덟 칸뿐이고 `rawDatasetName` 조차 없다.
- `tasks`: 학습 유형(모방/강화, 복수) 컬럼 추가. 모방 전용 4개 컬럼 nullable. **강화학습 태스크는 `tasks` 에 저장하지 않는다** — 학습 요청에서 고르므로 `trainings`(또는 학습 요청 레코드)에 붙는다.
- **학습 1 : N 체크포인트 — 2026-09-22 로 철회. 3차는 1 : 1 이다.**
  - **3차 스키마 변경은 한 칸뿐**: `training_runs.rollout_artifact_id BIGINT` 추가. **새 테이블 없음.** `model_artifact_id` 는 뜻도 안 바뀐다("대표 모델" 개념 자체가 사라진다).
  - **왜 철회했나**: ⑥ 체크포인트 관리를 3차에서 빼기로 했는데(§7), 한때 "`training_run_checkpoints` 는 ④-b 목록이 어차피 쓰니 스키마만 미리 넣자" 고 적었다. **앞뒤가 안 맞았다** — 그 테이블이 필요한 이유가 바로 목록·대표 지정·선택 다운로드이고, 그게 곧 체크포인트 관리다. 더 나쁜 건 **행을 쌓으면 체크포인트마다 아티팩트가 storage 에 올라간다**는 것이다. **차기 시작하는데 지울 방법이 없는 상태**가 되고, 그건 아무것도 안 하는 것보다 나쁘다. 새 테이블 추가는 기존 컬럼 변경이 아니라 순수한 추가라서 4차에 해도 싸다. (사용자 지적: *"체크포인트 관리를 없애면 ④-b 목록에서 `training_run_checkpoints` 테이블도 없어지는 거 아닌가? 나중에 체크포인트 관리 기능 개발할 때 건드리는 게 낫지 않나?"*)
  - **딸려 빠진 것 다섯**: `training_run_checkpoints` 테이블 / MS → DL 의 체크포인트 통보 종류 / ④-b 의 체크포인트 목록·`대표로 지정`·선택 다운로드 / ② 의 "중간 체크포인트도 모델로 등록" 토글(= 정확히 1:N 스위치) / 롤아웃 간격(끝에 한 번만 찍으면 간격 개념이 필요 없다).
  - **잃는 것**: 강화학습은 마지막이 최고가 아닌 경우가 흔한데(보상은 오르고 걸음은 망가진다) **다른 iteration 을 DL 에서 고를 수 없다.** 대가를 치를 수 있는 이유는 **MS 에 이미 있다**는 것 — `model-studio/frontend/src/pages/Checkpoints.tsx`, 사이드바 `체크포인트 / 모델 결과`. 다만 **다운로드 버튼은 없고 `경로 복사` 뿐**이라 학습 PC 경로로 가져가야 한다. 강화학습을 돌리는 사람은 그 PC 를 쓰는 사람이라 3차에서는 받아들인다.
  - **경계로 보면 오히려 깔끔하다**: MuJoCo 테스터를 뺀 논리와 같다 — 어느 체크포인트를 쓸지 고르는 것도 학습 도구의 일이고, DL 은 등록된 결과 하나를 보여 준다. ③-b 중지 모달이 이미 "마지막 체크포인트를 모델로 등록하시겠습니까" 를 묻는 구조라 등록 결정은 원래 MS 쪽에 있었다.
  - **4차에 1:N 을 켤 때의 안은 그대로 보존한다(2026-09-20 작성)**: 새 테이블 `training_run_checkpoints (training_run_id, iteration, model_artifact_id, rollout_artifact_id, created_at, UNIQUE(training_run_id, iteration))` + `training_runs.model_artifact_id` 의 뜻을 **대표 모델**(기본값 = 마지막)로 전환 + status 엔드포인트에 `CHECKPOINT` 종류 추가. 컬럼을 그대로 두고 뜻만 바꾸면 기존 다운로드 경로와 FE 의 `modelArtifactId == null` 판정이 안 깨진다. **대표를 사용자가 바꿀 수 있어야 하는 이유**(마지막이 최고가 아니다)와 **다운로드 기본값을 "전부 받기" 로 두지 않는 이유**(모방학습 체크포인트는 개당 수백 MB~GB)도 그때 근거 그대로 유효하다.
  - 참고: **덮어쓰기가 아니다.** 강화학습은 `rsl_rl/runners/on_policy_runner.py:286` 이 `model_{it}.pt` 를 따로 쓰고, 모방학습은 `model-studio/backend/main.py:2797` 이 번호 붙은 체크포인트 디렉터리를 이미 목록으로 준다. 덮어쓰이는 건 `checkpoints/last` 하나뿐. **즉 MS 파일시스템에는 계속 쌓이고, 3차에서는 그걸 DL 로 안 가져오는 것뿐이다.**
- `robots`: URDF/USD/MJCF artifact 참조 컬럼 추가. 지원 로봇은 시드.
- `robots.robot_key`(예: `agibot_x2`) 추가. 같은 로봇의 이름이 지금 세 가지다 — URDF 는 `<robot name="X2-Ultra">`, 코드 디렉터리는 `agibot_x2`, DL 관리자 모델명은 `X2 Ultra`. 강화학습 태스크 목록을 로봇으로 맞출 때 **모델명으로 매칭하면 깨진다.** DL 과 학습 레포가 같은 `robot_key` 를 쓴다.
- 강화학습 지원 매트릭스(로봇 × 태스크)는 DB 가 아니라 학습 워커가 API 로 내려 준다.

**왜 뒤집었나 (사용자 지적 그대로)**

- **"탐색 진입 페이지도 빼고, 탐색 버튼 누르면 바로 탭 보여주는걸로. 허허벌판 같다는 의견"** — 검색창 하나와 진입 카드 두 장만 놓인 화면은 들어와도 볼 게 없고, 무엇을 검색해야 하는지도 알려 주지 않는다. 열자마자 목록이 깔리는 쪽이 맞다.
- **"통합 검색은 제외하고, 검색하면 바로 탭이 뜨고"** — 통합 검색 결과는 종류별 섹션 + 좁히기 블록까지 갔지만, 그래도 전용 화면에 닿으려면 **클릭이 한 번 더** 필요했다. 종류가 둘뿐인데 중간 화면을 두는 값이 안 나온다.
- **탭 이동 시 검색어는 들고 가되 조건은 버린다.** 겹치는 필터가 **로봇 모델 하나뿐**이라(제조사는 로봇 모델을 고르면 따라오므로 학습 탭에서는 뺐다) 절반만 따라오면 사용자는 뭐가 남았는지 모른다.
- **조건은 전부 URL** — `/explore/tasks?q=걷기&cat=LOADING&robot=X2&page=2`. 필터 토글은 `replaceState`, 탭 이동·상세 진입만 `pushState`. 근거는 아래(2026-09-16 에피소드 목록 민원 2건)와 같다.

### 학습 상태 필터는 없앤다 — 탐색은 성공한 학습만 보여준다 (2026-09-21)

`model_artifact_id IS NOT NULL` 을 항상 건다. 그러면 이 목록이 곧 "받을 수 있는 것들" 이 된다. 진행중 · 실패는 ④ 학습 관리에서 본다. 시안 카드에 `학습 기간 {시작} – {종료}` 가 있는 것도 끝난 것만 전제한다는 뜻이라 일치한다.

| **⑤-d 작업 찾기** | 지금 탐색 결과 화면 거의 그대로 — 좌측 필터 4종 + 카드 목록 |

**확정된 세부**

- **손잡이는 섹션당 하나.** 한때 상단 탭 · `⌄ N개 더` · 좁히기 블록 셋이 있었는데, 탭은 좁히기 블록과 **목적지가 같았고** `N개 더`는 12개를 그 자리에 펼쳐 아래 섹션을 밀어냈다. 둘 다 뺐다.
- **좁히기 블록은 흰 바탕 · 진한 테두리 · 채운 버튼.** 연회색 + 화살표만이면 각주처럼 읽혀 "조건을 걸 수 있다"가 안 보인다. 블록 안에 **조건 이름을 나열**한다(작업 4 / 모델 5) — "전체 보기"라고만 쓰면 "같은 걸 더 본다"로 읽힌다.
- **섹션마다 카드 2개.** 카드 214px(썸네일 166 + 여백 24×2), 본문 세로 714px → `헤더 35 + 카드 2×214 + 사이 16 + 블록 72` = 567px. 3개면 813px 라 한 섹션도 안 들어간다.
- **어떤 2개냐 = 최근 것.** BE 검색이 `ILIKE %q%` 라 관련도 점수가 없다(`TaskReader.kt:324`). 작업은 `tasks.updated_at`, 모델은 `training_runs.started_at`.
- **조회 조건은 전부 URL 이 들고 화면은 읽기만 한다.** 필터 토글은 `replaceState`, 화면 이동만 `pushState`. 뒤로 가기가 화면 단위로 움직이고 각 화면의 마지막 조건이 살아 있다. 링크 공유도 된다.
  - **근거: 2026-09-16 에피소드 목록 민원 2건**(상세 갔다 오면 필터 풀림 / 6페이지 '다음'이 엉뚱한 데로 튐)의 뿌리가 *조회 조건이 URL 에 없고 `useState` 에만 있던 것*이었다. 같은 실수를 반복하지 않는다.
- **받아들인 비용**: 탭이 없으니 모델 찾기 ↔ 작업 찾기를 바로 못 옮긴다(통합 결과로 돌아가야 한다). 조건이 URL 에 있어 돌아가도 상태는 살아 있고, 종류를 갈아타는 일이 잦지 않다고 봤다.
- **종류 전환은 전용 화면에만 둔다(2026-09-21).** 통합 결과에서는 좁히기 블록과 목적지가 같아 뺐지만, 전용 화면(⑤-c·⑤-d)에서는 반대쪽으로 갈 길이 그것뿐이다. 제목 위에 `작업 54 / 모델 24` 두 칸. **옮길 때 검색어는 들고 가되 조건은 버린다**(두 종류의 필터가 절반만 겹친다).
- **⑤-c 의 "걸린 조건" 칩 줄은 뺐다** — 왼쪽 필터 패널이 이미 같은 것을 보여 준다. 한 화면에 같은 상태를 두 군데서 그리면 어긋날 자리만 는다.
- **⑤-c 의 날짜 열은 시작일 하나로 줄였다.** 필터 패널이 들어와 표 폭이 868px 뿐이고, 정렬이 학습 시작 일시 최신순이라 시작일만 있으면 읽힌다.
- **필터 패널 폭은 두 화면 모두 300px 로 맞춘다**(기본 `.xfilter` 는 376px). 모델 쪽 표가 들어갈 자리를 확보하려고 줄인 건데, 작업 쪽만 376px 로 두면 **종류를 바꿀 때 패널 폭이 흔들린다.**
- **알려진 우려 — 종류 전환 UI 의 모양이 동작과 안 맞는다(2026-09-21).** 세그먼트 컨트롤은 "딸깍 하면 그 자리에서 바뀐다" 로 읽히는데, 실제로는 **주소가 바뀌고 API 를 새로 부르며 걸린 조건도 버린다.** 지금은 모양만 잡아 둔 상태이고, 실제 구현 전에 표기를 다시 봐야 한다(링크형/탭형/버튼형 중 어느 쪽이 맞는지).
- **작업 유형 카드를 뺀 이유**: 진입 카드 `작업 찾기` 와 하는 일이 겹치고, 카드 8장이 아래에 깔리면 검색창이 화면 위로 밀려 이 화면의 주인공이 흐려진다. 유형별 바로가기는 작업 찾기의 **작업 유형 필터**가 같은 일을 한다.
- **미정**: 작업 찾기의 정렬. 지금 이름순 고정인데 검색어를 들고 온 경우엔 `updated_at` 최신순이 맞다 — FE·BE 합의 필요.

### [7] 탐색의 두 번째 엔티티를 뭐라 부를까 — **2026-09-21 결론: 학습**

사용자 질문: *"데이터 라이브러리에서는 '학습' 이라는 실행 행위를 엔티티로 규정하고, 그 안에 '모델' 은 그저 artifact_id 일 뿐이다. 그래서 질문은 '학습'? '모델'? 뭐가 맞을까? 원래 시스템 초기에는 '학습 모델' 이라고 했었거든."*

**결론: `학습`.** 세고 · 고르고 · 지우고 · 정렬하는 것은 **학습**, 내려받는 것은 **모델**. 이 규칙은 이미 제품이 지키고 있었다.

- **모델은 스스로를 구별하지 못한다.** 내려받는 파일 이름이 `${runName}.zip` 이다(`useTrainingRunsQuery.ts:74`) — 모델에 부를 이름이 없어 학습 이름을 빌려 쓴다. `V36` 에도 `model_artifact_id BIGINT` 한 칸뿐이고 이름 · 버전 · 스테이지가 없다. 그래서 목록에 늘어놓을 수 있는 축이 **전부 학습의 속성**이다. 계보 카드가 이를 증명한다 — 카드에 모델 고유 정보는 `{모델유형}` 하나뿐이고 그것도 ACT/GR00T/PPO, 즉 알고리즘이지 그 모델의 정체성이 아니다.
- **i18n 이 이미 갈라 놓았다.** 학습 쪽: `해당하는 학습이 없습니다` · `조회된 학습:` · `선택한 학습 {{n}}개` · `학습 이름` · `학습 일시` · `학습 시작 일시 최신순` · `{{n}}개의 학습을 삭제하였습니다` · 사이드바 `학습 관리`. 모델 쪽: `모델 다운로드` · `모델 유형` 둘뿐. 한 문장에 같이 나오기도 한다 — `{{n}}개의 모델을 다운로드하였습니다. 학습에 실패한 모델은 제외됩니다.`
- **탐색 화면이 이미 `학습` 이라고 쓴다.** `explore.taskResultCountsSummary = "… 학습 데이터 {{n}}개 · 학습 {{trainingRunCount}}개"`. 탭을 `모델` 로 두면 같은 화면에서 같은 것을 두 이름으로 부르게 된다.
- **`모델` 은 이미 로봇 모델이 점유했다.** 같은 필터 패널에 `로봇 모델` 이 서 있다(`task.robotModel`, `episodeViewer.robotModel`).
- **체크포인트가 숫자를 갈라놨다.** ④-b 에서 `training_run_checkpoints` 를 신설해 **학습 1 : 모델 N** 이 됐다. 학습 24건이어도 모델은 수백 개일 수 있어 `모델 24` 는 **틀린 숫자**다.
- **지금 `모델` 이라 부르면 없는 걸 약속한다.** 모델을 1급 엔티티로 쓰는 제품(MLflow Model Registry 등)은 모델에 이름 · 버전 · 스테이지를 준다. 우리에겐 없다. 나중에 정말 모델 레지스트리를 만들 때 쓸 이름을 **아껴 둔다.**
- **`학습 모델` 은 아니다.** i18n 에 딱 하나 남아 있는데 키가 `selectRobotModelTrainedModelWill` — "학습**된** 모델" 의 준말이지 엔티티 이름이 아니었다. `학습 데이터` 와 나란히 두면 층위가 섞인다(하나는 입력, 하나는 실행).

**"고객이 찾는 건 결국 모델 아니냐" 는 반론**은 맞다. 다만 **이름이 아니라 동선으로 갚는다** — 계보 카드가 상세로 들어가기 전에 판단할 정보를 충분히 주고(계보 · 학습 유형 · 학습 기반 · 로봇 · 기간 · 스텝수), 학습 탭 결과 헤더에 `학습을 열면 모델을 내려받을 수 있습니다` 한 줄을 둔다. (한때 "목록에서 바로 다운로드" 를 제안했으나 사용자가 반려 — [6] 참조.)

**적용 범위**: 탐색 탭 `학습`, ④-b `모델 상세` → **`학습 상세`**, 작업 카드 meta `학습 N개`(현행 유지). 그대로 두는 것: `모델 다운로드` · `대표 모델` · `모델 유형` · `마지막 체크포인트를 모델로 등록`.

**지난 안은 지우지 않고 남겼다** — ⑤-x1(결과 A안) · ⑤-x2(B안) · ⑤-x3(C안) · ⑤-x4(카드 4종). 전부 `보류` 배지.

**뺀 것 · 보류**
- **원본 데이터 · 학습 데이터 탐색은 뺀다.** 작업에 종속된 중간 산출물이라 작업 밖에서 찾을 이유가 거의 없다. 화면이 넷이 되는 값어치가 없다.
- **⑤-b/c/d (결과 A·B·C안)과 ⑤-e (카드 4종)은 보류.** 한 화면에 두 종류를 섞을 때의 안이라 분리하기로 한 이상 쓸 데가 없다. 사용자 요청으로 **지우지 않고 비교용으로 남긴다**(캡션에 `보류` 배지).
- **성능 지표 검색은 별도 과제로 뺀다.** DB에 모델 성능이 없다 — `episode_stats` 는 학습 데이터 집계지 모델 성능이 아니고, 강화학습 보상은 로그 아티팩트 안인 데다 **작업마다 스케일이 달라 작업 간 비교가 불가능**하다. 하려면 "평가(evaluation)" 개념을 새로 만들어야 한다.

### ⑥ 학습 체크포인트 관리 — **3차 개발 범위 제외 (2026-09-22)**

사용자 지시: *"과감하게. 3차 개발 범위에서 '체크포인트 관리' 는 빼자."*

**빠지는 것은 보관 정책과 정리 기능 하나다.** ④-b 의 체크포인트 목록과 대표 지정은 **남는다**(학습이 끝나면 바로 필요하고, 이미 있는 목록을 끌어다 붙이는 일이다).

**왜 뺄 수 있나**

- **손실이 거칠지만 막혀 있지는 않다.** 저장소가 차면 지금도 손은 있다 — **학습을 통째로 지우면 딸린 아티팩트가 정리된다**(`artifact_deletions`(V35) + `ArtifactDeletionSweeper`). 체크포인트만 골라 못 지워서 학습 파라미터·로그·롤아웃까지 같이 날아가는 게 대가다. 막혀 있었다면 미룰 수 없었다.
- **데이터가 유실되는 방향의 위험은 없다.** 덮어쓰기가 아님을 확인해 뒀으므로 **안 지우는 쪽이 기본값**이고, 정리 기능이 없어서 생기는 문제는 "용량" 하나로 좁혀진다. 반대 방향(급히 만들었다가 지우면 안 되는 걸 지운다)이 훨씬 비싸다.
- **19개는 아직 가상의 수치다.** 지금 실제로 쓰는 건 사실상 마지막 것 하나다. **여러 개를 정말 쓰기 시작할 때**가 이 기능이 필요해지는 시점이다.

**3차에서 해두는 것 — 미루는 대가로 치르는 최소 조치 셋**

1. **스키마는 넣는다.** `training_run_checkpoints (training_run_id, iteration, model_artifact_id, rollout_artifact_id, created_at, UNIQUE(training_run_id, iteration))`. ④-b 목록이 쓰는 테이블이라 어차피 필요하고, 나중에 **마이그레이션을 두 번 하지 않는다.** 행은 쌓이고 지우는 UI 만 없다.
2. **용량을 보여만 준다.** ④-b 체크포인트 목록에 개당 크기와 합계를 적는다. 정리 버튼은 없어도 "차고 있다" 는 보여야 한다 — 표시 한 줄이라 싸고, 아래 방아쇠를 사람이 알아차리는 유일한 통로다.
3. **롤아웃 간격 기본값을 넉넉히 잡는다.** 기본 `save_interval = 100` 이면 18,400 iteration 에서 184편, 와이어프레임 기준 **1,000** 이면 19편 — 10분의 1 이다. 간격 하나로 4차까지 버틴다.

**언제 다시 보나 — 방아쇠 (조건으로 적어 둔다)**

- 모방학습 체크포인트를 **실제로 여러 개 쓰기 시작할 때**(중간 것을 골라 쓰는 일이 생기는 순간).
- 운영·납품 PC 의 **storage 사용량이 임계에 닿을 때**(④-b 용량 표시가 알려 준다).
- 고객사가 **"지난 체크포인트를 지우고 싶다"** 고 말할 때 — 학습을 통째로 지우라고 안내할 수 있는지가 판단 기준이다.

**정해야 할 것 (4차로 넘긴다)**
- **몇 개를 남기나** — 전부 / 최근 N개 / 대표 + 최종만. 모방학습과 강화학습에 같은 규칙을 쓸 수 있나(개당 5~10MB vs 수백 MB~GB, **용량이 100배 차이**다).
- **언제 지우나** — 학습 종료 시 정리 / 기간 만료 / 용량 상한 도달 시. 자동인가 사람이 누르나.
- **대표로 지정된 체크포인트는 못 지우게 하나** — 지우면 `model_artifact_id` 가 가리킬 데가 없어진다.
- **롤아웃 mp4 는 모델과 같이 지우나 따로 두나** — 영상은 작아서(수 MB) 오래 둬도 된다.
- **누가 지우나** — 사용자 / 관리자 / 자동. 지금 학습 기록 삭제 권한은 `createdBy` 기준이다(`TrainingRunAccessPolicy`).
- **MS 와 DL 중 누가 원본을 들고 있나** — 지금은 MS 파일시스템에 있고 DL 은 아티팩트 id 만 안다.

화면은 **4차에서**, 정책이 정해진 뒤에 그린다. ④-b 의 체크포인트 목록에 **정리 버튼**이 붙는 정도가 될 것으로 본다 — 3차에 넣는 **용량 표시**가 그 자리를 미리 잡아 둔다.

### ⑦ 원본 데이터 묶음 다운로드 — **3차에 만든다 (2026-09-27 결정, 2026-09-28 화면)**

**뒤집힌 결정이다.** 현장에서 해달라는 말이 많았다는 것이 이유(사용자). 처음엔 *"묶어 주는 기능을 새로 만드는 일"* 이라 뺐는데, `storage` 를 확인해 보니 **아티팩트 하나를 무압축으로 흘려보내는 길이 이미 있어**(`dcs/files.py:97`, `ZipStream` + `Content-Length`) **그 길을 넓히는 일**이었다.

**받는 방식 — 브라우저에 맡긴다 (2026-09-28 확인, 이번 세션의 제일 중요한 발견)**

사용자 질문이 출발점이었다 — *"모델 다운로드는 그냥 버튼 누르면 브라우저에서 받아지던데, 이것도 그게 되나?"*

- **지금 방식 그대로는 안 된다.** 모델 · 로그를 받는 길은 `responseType: "blob"` 으로 받아 `URL.createObjectURL` 로 저장한다(`api/artifacts.ts:10` · `components/training/TrainingCodeSection.tsx:41` · `utils/downloadBlob.ts:16,26`). **파일 전체가 브라우저 메모리에 한 번 올라간다.** 모델 zip 은 괜찮고 GB 단위 묶음은 탭이 죽는다.
- **그런데 "주소를 그냥 여는" 길은 이미 제품 안에 있다.** `storageClient` 에는 **인증 헤더 인터셉터가 없고**(`api/storage.ts` — 업로드만 `X-Upload-Ticket` 을 따로 싣는다), `getFileUrl()` 이 만든 `/library-storage/...` 주소가 이미 `<img src>` 에 그대로 꽂혀 돈다. 결정적으로 **BE 가 그 주소를 그대로 내려주고 있다** — `logDownloadUrl`(`TrainingRunService.kt:107`)이고 타입 주석이 *"브라우저가 저장소에서 직접 받는다(BE를 지나지 않는다)"* 라고 못 박아 뒀다(`api/types.ts:372`).
- **결론: blob 을 거치지 말고 주소를 그대로 연다.** 진행률 · 남은 시간 · 저장 위치를 브라우저 기본 다운로드가 처리하므로 **제품에 다운로드 창을 만들지 않는다.** `Content-Length` 가 실려 있어 진행률도 나온다.

**정해진 것**

- **상한 = 에피소드 1,000개** (사용자, 2026-09-27). **개수 기준만이고 용량 기준은 3차에 두지 않는다** — 에피소드 평균 용량을 아직 재지 않았다. 숫자를 1,000 으로 잡은 이유는 **등록 상한이 이미 그 숫자**라서다(`i18n/locales/ko.json:264` — "1회 최대 1,000개의 에피소드를 한 번에 등록할 수 있습니다"). 두 숫자를 다르게 두면 사용자가 둘을 외워야 한다.
- **전체 받기와 골라 받기가 같은 화면에 있다.** 상한에 걸렸을 때 빠져나갈 길이 그것뿐이기 때문. 다행히 **새로 만들 것이 버튼 하나뿐**이다 — 에피소드 목록에는 여러 개를 골랐을 때 뜨는 줄이 이미 있고(`복제` · `일괄 QA` · `삭제` — `EpisodeSelectionBar.tsx:67-95`), **페이지를 넘어도 선택이 유지된다**(`IDS` / 제외 목록 두 방식 — `SourceDataDetailPage.tsx:132-137`).
- **누르면 그 자리에서 시작한다.** 미리 만들어 두고 나중에 알리는 방식은 **제품에 사용자를 부를 수단이 없어** 성립하지 않는다(사용자 지적).
- **푼 뒤 에피소드 단위 폴더.** 이름만 보고 어느 에피소드인지 알 수 있어야 한다.
- **화면 안의 버튼 자리는 디자인이 정한다**(사용자).

**남는 것**

- **`storage` 는 다른 팀이 맡고 있다** — 여러 아티팩트를 한 묶음으로 내보내는 일은 미리 맞춰야 한다.
- **압축 형식(zip · tar)은 개발이 정한다.** 제품이 약속하는 것은 "파일 하나로 받는다" 까지다.
- **⚠ 이어받기가 안 된다.** 요청마다 새로 조립해 오프셋이 고정되지 않는다(`files.py` docstring). 끊기면 처음부터 — **상한을 두는 진짜 이유**다. 다만 재시도 · 분할을 어떻게 할지는 **구현하는 쪽 몫**으로 두고 제품이 강제하지 않는다(사용자).

**옛 사실 기록(2026-09-21)**: `episodes.artifact_id` 는 `NOT NULL UNIQUE`(V19) 라 에피소드 하나는 지금도 받을 수 있다(UI 가 없을 뿐). `raw_datasets` 에는 `artifact_id` 가 없다.

### ⑨ 복제 · 병합 실패 사유 (2.5차 QA · KI-08, 2026-09-23 추가)
**QA 메모의 진단이 틀렸다. 문구 문제가 아니라 집계 문제다.**
- QA: 7,390건 병합 도중 원본을 지우자 **390건이 전부 `DE_UNAVAILABLE`** — 「저장소 서버에 연결하지 못했어요. 잠시 후 다시 시도해주세요.」
- **"저장소 장애와 원본 소실이 같은 코드로 뭉쳐 있다" 는 사실이 아니다.** `SOURCE_MISSING` 은 이미 별도 코드고(`EpisodeCopy.kt:74`), 문구도 이미 원하는 그대로다 — `error.episodeCopy.SOURCE_MISSING=원본 파일을 찾을 수 없어요. 복제하는 동안 삭제됐을 수 있어요.`(`messages.properties:120`). DE 도 항목별로 `source_missing` 을 준다(`storage/src/dcs/control.py:427`). **제안대로 코드를 가르고 문구를 바꿔도 아무것도 안 달라진다 — 그 길로는 안 지나가기 때문이다.**
- **진짜 원인: 배치 전체가 400 으로 튕긴다.** DCS 는 복사 전에 **사전 검증**을 한다(`control.py:413-418`) — `SELECT id, type FROM artifact WHERE id = ANY(...) AND status='ready'` 로 조회해 **하나라도 없으면** `ApiError(400, "bad_request", "not found or not ready: [...]")`. **항목별이 아니라 배치 통째로 400.** 항목별 `source_missing` 은 사전 검증 통과 후 `_copy_one` 사이의 **찰나의 경합**에서만 나온다(`control.py:425-428`). 병합이 도는 도중에 원본을 지우면 아직 안 보낸 배치의 id 는 **보내기도 전에** 사전 검증에 걸린다.
- **BE 는 그 400 을 구분하지 않는다** — `DeArtifactClient.copyArtifacts` 는 `catch (e: Exception)` 하나로 받아 `allFailed(artifactIds, DE_UNAVAILABLE)`(`DeArtifactClient.kt:145-147`). **배치 100건 전부**를 연결 실패로 적는다. 같은 파일의 **삭제** 쪽엔 `HttpClientErrorException` 분기가 있다(`:90-97`) — **복제만 없다.**
- **숫자가 맞는다**: `COPY_BATCH_SIZE = 100`(`EpisodeCopyRunner.kt:27`), DCS `copy_ids_limit = 100`(`config.py:41`). 7,390 = 100×73 + 90, 실패 390 = **100+100+100+90** — **배치 네 개가 통째로** 죽은 것이다. 한 건씩 실패했다면 나올 수 없는 수다.
- **그래서 문구보다 집계가 더 나쁘다.** 390건 중 실제로 사라진 원본은 일부고 나머지는 **멀쩡한데 복사도 안 해 보고 실패로 적힌 것**이다. 다시 돌리면 대부분 복사된다 — 「잠시 후 다시 시도해주세요」 는 **이유는 틀렸는데 행동만 우연히 맞는** 안내다.
- **고칠 자리 두 안** — (a) DCS 가 사전 검증의 "없음" 도 항목별 `source_missing` 으로 내린다(HTTP 200). 대신 `control.py` 주석이 지킨다고 적은 *"호출측 결함이면 아무것도 만들지 않는다"* 를 포기하고, **진짜 잘못된 id 와 지워진 id 를 구분할 수 없게 된다.** (b) **권장** — DCS 는 400 을 유지하되 본문에 없어진 id 목록을 **기계가 읽게** 싣는다(지금은 메시지 문자열뿐이라 파싱이 위태롭다). BE 가 없어진 것만 `SOURCE_MISSING` 으로 적고 **나머지는 다시 보낸다**. DE 계약도 "아무것도 만들지 않는다" 도 지킨다.
- 그 외 정해야 할 것: 남은 건을 BE 가 자동 재시도할지(하면 **한 번으로 제한**) / 병합 중 원본 삭제를 애초에 막을지(막으면 경합은 사라지나 잠금 범위가 커진다) / 실패 목록을 사유별로 묶어 보여줄지(390건이면 같은 문구가 390줄).
- **화면은 안 바뀐다.** 고칠 자리는 DCS `control.py:413-418` 와 BE `DeArtifactClient.kt:115-148` **두 곳**이고, 문구 · 코드는 이미 있는 것을 쓴다.

**2026-09-29 (5) — 빈 상태를 다시 잡았다 (V84)**

- **지적 두 가지.** *"바뀐게 아예 없을때에 대한 와이어 프레임 화면은 전혀 없는데...? 내가 아까 말했던건 ... 기준값에서 변경된 내역이 없습니다 를 보여주고, 그 아래에는 그냥 접힘으로 보여주자 이랬던것같은데 아니야?"* — **둘 다 맞다.**
- **[1] 화면이 없었다.** 사용자는 *"화면에 추가해줘"* 라고 했는데 나는 **④-b-2(비교 기록)에 설명 스트립**으로만 넣었다. 비교 기록은 *고르기 위한 자리*라 거기 그린 것은 화면이 아니다. **④-b 에 상태 프레임을 넣었다** — `statelab` 관용구(이미 11군데 쓰고 있다)를 써서 `④-b -1 · 기준값에서 바꾼 항목이 있을 때(기본)` / `④-b -b · 바꾼 항목이 하나도 없을 때` 두 장으로 가르고, 뒤쪽은 **학습 파라미터 부분만** 잘라 그렸다.
- **[2] 결정된 안은 「문구 + 접힘」이었다.** 표 자리에 **`기준값에서 변경된 내역이 없습니다`** 한 줄만 두고 **11개는 접은 채로** 둔다. 내가 적었던 *"전부 펼치고 띠 없앰"* 은 **바꾼 게 없는 학습일수록 화면이 길어지는** 반대 결과가 된다 — 접어 두면 표 길이가 상황에 따라 요동치지 않는다.
- **띠 규칙이 하나로 정리됐다.** **「기준값 그대로인 항목」이 하나라도 있으면 띠를 그린다.** 0개 바꿈이면 11개가 접히고, 전부 바꿈이면 그 수가 0 이라 띠가 없다. 상태별 예외가 아니라 한 줄짜리 규칙이다.
- **빈 표에 머리행은 안 그렸다.** 접힌 상태에서는 `항목 / 설정 키 / 값` 헤더 아래에 아무 행도 없어서, 헤더를 빼고 안내 한 줄 + 띠만 뒀다. 펼치면 헤더와 11행이 같이 나온다. (이건 내가 정한 렌더링 세부다 — 헤더를 남기는 쪽이 낫다면 되돌리면 된다.)
- **기획서**: `학습 상세` 9 를 다시 썼다. **와이어프레임 ④-b-2** 의 스트립도 결정안으로 고치고, *"펼치자는 안도 있었다"* 로 기각 사유를 남겼다. w-s28 의 *"아직 아무것도 기획서에 반영하지 않았다"* 는 이제 거짓이라 *"고른 뒤 기획서까지 반영했다"* 로 고쳤다.
- **되풀이된 실수.** 정해지지 않은 내 안을 적용한 게 **오늘만 두 번째**다(첫 번째는 3안 선반영 — *"아니, 이걸 바로 적용하면 어떡하니...?"*). **사용자가 방향을 말한 항목은 그 말대로 그리고, 내 대안은 「왜 이렇게 했나」에 후보로만 적는다.**
- **"화면에 추가" 는 화면에 추가하는 것이다.** 비교·검토 섹션(④-b-2 같은)에 그리는 것은 *기록*이지 화면이 아니다. 상태를 요청받으면 **그 화면 섹션에 `statelab` + 프레임**으로 넣는다.

| **18 원본 데이터 상세 — 새로 그릴 것** | ~~화면 3장~~ → **2026-10-01 정정: 새로 그릴 우리 화면은 없다.** 누르면 **저장 위치 고르기**(브라우저 · OS 창 — **우리가 만들지 않는다**, 흐름에만 표시) → **바로 받기**. 집계 중 · 개수 · 용량 확인 모달은 **그리지 않는다**(뺐다). 대신 **오른쪽 아래 진행 패널** — 에피소드 업로드 패널(`EpisodeUploadQueuePanel`)과 **같은 컴포넌트**라 새로 그릴 건 **문구뿐**: 머리줄 `원본 데이터 다운로드 준비 중 / 다운로드 중 / 완료`, 항목 `파일명 · 에피소드 218개 압축 중` → 막대 + `37%` → 성공 태그. **취소 버튼 없음.** 와이어프레임 **⑦ -1 ~ -4**(-3 압축 중 · -4 다운로드 중) | 구글 드라이브 폴더 다운로드처럼 **용량을 알리지 않는다** — *"용량으로 막는 건 브라우저나 사용자의 책임"*. 받는 중 표시는 **브라우저가 안 띄우는 방식**이라 우리가 띄운다 (37) |

### 10-2. 시안이 맞아 **기획서를 고친 것** 3건

| 무엇 | 기획서가 이랬다 | 시안이 이래서 바꿨다 |
|---|---|---|
| **작업 수정 · 학습 유형** | 값 한 줄로 내린다 | **생성 Step 1 에서 고른 카드가 그 모양 그대로 잠겨** 있으니 *"내가 무엇을 골랐나"* 가 한눈에 읽힌다 (30) |
| **학습 상세 · 제목** | 제목 옆에 상태 이름 | **점만** 찍는다 — 이름은 목록에서 이미 봤다 (`학습 상세` 1) |
| **데이터 탐색 · 필터와 개요** | 작업 탭 필터 4종 / 개요 값 개수 고정 | **작업 탭에 학습 유형 필터**를 더하고(4종 → 5종), **개요 값 개수는 화면마다 다르게** — 탐색 5, 작업 안 학습 관리 4 (33) |

### 10-3. 같은 날 반영한 곳

- **노션 기획서** — 02 용어 규정(학습 상태 5종 · `스텝` 신설 · 실행 파라미터 순서) · 03 구현 범위 · 정책 4 · 5 · `작업 수정` · `학습 상세` · `데이터 탐색` · `학습 실행 현황` · `원본 데이터 묶음 다운로드` · **05 「다운로드 동시 실행 제한」 신설** · **06 뒤집힌 결정 28~33 신설** · 바깥 자료 8 · 9.
- **연동 스펙 (MS → DL)** — 상태 코드 **`SUCCEEDED` → `FINISHED`**, **`STOPPED` → `EARLY_FINISHED`**, 화면 표시 ko/en, `planned_steps` 단위 정의, §6 에 **이름 변경 마이그레이션 행** 추가. ⚠️ **성복님과 합의한 문서**라 바뀐 내용을 알려야 한다.
- **와이어프레임 V91** — 상태 이름, `스텝` 통일(설정 키 `max_iterations` 와 실시간 로그는 그대로), 실행 파라미터 순서 · 단위 · `Headless: 사용`, 개요에서 학습 유형을 빼고 **`스텝` + 말풍선** 추가, ⑦ 다운로드 3걸음(V90).

### 10-4. 검수하며 알게 된 것

- **`step` 은 강화학습에서 이미 다른 뜻으로 쓰인다** — 환경 타임스텝. 같은 이름으로 보내면 **자릿수가 몇 개씩 어긋난 채로 타입 검사를 통과한다.** 연동 스펙 §3 · §5 에 못박았다.
- **상한은 무엇을 지키는지부터 물어야 한다** — 사용자 디스크는 지킬 수 없고(브라우저가 여유를 모른다), 서버는 **동시 요청 수**로 지킨다. 크기로 막으면 **큰 것 하나를 받는 정상적인 사용만** 막힌다.
- **에피소드 하나가 1MB일 수도 500MB일 수도 있다** — 수량 상한은 **같은 숫자가 500배 다른 일**을 가리킨다.

## 11. 2026-10-01 — ⑦ 원본 데이터 다운로드 예고 삭제 (V95)

- **바뀐 것** — 흐름이 **저장 위치 → 바로 받기** 두 걸음이 됐다. **집계 중 모달 · 개수 · 용량 확인 모달(⑦ -3 · -4)을 지웠다.** 목록에도 받기 전에도 용량 · 개수를 싣지 않는다.
- **왜** — 구글 드라이브의 폴더 다운로드가 그렇다: 용량을 알리지 않고 바로 압축하고, 준비되면 저장 위치를 묻고 받는다. *"용량으로 막는 건 브라우저나 사용자의 책임"*(사용자). 드라이브의 「준비 중」 단계는 서버가 zip 을 먼저 만들기 때문에 있는 것이고, 우리는 `storage` 가 흘려보내므로 그 단계가 없다.
- **같이 빠진 근거** — 「저장 위치가 먼저인 이유(합계를 미리 안 세니 폴더 고르는 시간으로 덮는다)」 · 「이어받기가 안 되니 얼마를 거는지 알아야 한다」 · 「예고는 원본 데이터에만(모델은 크기를 이미 안다)」 — 전부 예고가 있을 때의 이야기라 ⑦ 의 `왜` 에 기록으로만 남겼다.
- **치르는 값** — 15GB 인 줄 모르고 눌렀다가 20분 뒤에 아는 일, 끊기면 얼마를 잃었는지도 모르는 것. 감수.
- **같은 날 정정 — 받는 중 표시는 제품 몫.** 저장 위치를 우리가 묻고 고른 자리에 흘려 쓰는 방식에서는 브라우저가 다운로드 표시를 띄우지 않는다(주소를 그냥 열 때만 나온다). 기획서 · 이 문서가 줄곧 *"진행률은 브라우저가 보여준다"* 고 적고 있었다 — 틀렸다. ⑦ -3 을 처음엔 「받는 중」 모달로 그렸다가, *"압축 파일이 짠 하고 만들어지는 게 아니잖아"* + 구글 드라이브가 업로드 · 다운로드에 같은 컴포넌트를 쓴다는 지적에 따라 **오른쪽 아래 진행 패널**로 바꿨다(V97) — 에피소드 업로드 패널(`EpisodeUploadQueuePanel`, 오른쪽 아래 고정 · 머리줄 + 접기 · 항목별 %)을 그대로 쓴다. 상태 `압축 중`(첫 바이트 전, `storage` 가 목록 세고 크기 확정) → `다운로드 중 N%`(`Content-Length` 로 %) → `완료`, 취소(받다 만 파일이 남지 않아야 한다 — 구현 몫). 화면을 막지 않는다. 문구는 기술적으로 무압축이어도 사용자가 아는 말 「압축 중」.
- **같이 정한 셋(패널 동작)** — [1] 토스트 없음, `저장` 누른 순간 패널이 뜬다. [2] 받는 중엔 X 도 **취소도 없음**(V101 에서 취소 버튼을 뺐다 — 끊는 길은 탭 닫기뿐), 완료되면 X. [3] 앱 안 이동은 계속 받고(업로드 큐처럼 앱 전체 컨텍스트), 탭 닫기 · 새로고침은 끊김 + 브라우저 경고 한 번. 끊기면 받다 만 파일은 남지 않아야 한다.
- **압축 파일 뒤처리(규칙 9 신설)** — 다운로드가 완료되면 바로 지운다. 사용자 사이에 공유되지 않고, 같은 원본 데이터를 다시 받을 때 이미 만든 압축 파일이 있는지 검사하는 로직은 없다 — 매번 처음부터. 흘려보내는 방식이면 지울 파일 자체가 없다. 구글 드라이브도 폴더를 받을 때마다 서버가 새로 묶고(매번 「압축 중」, 2GB 마다 분할) 묶은 zip 을 드라이브에 남기지 않는다 — 서버 안 재사용 여부는 공개 문서 없음(2026-10-01 조사).
- **참고 — 구글 드라이브는 2GB 마다 zip 을 나눈다(2026-10-01)** — `-001.zip`, `-002.zip`, 폴더 경계 무시. 우리는 **하나로 받는다** — 나누는 게 나은지 확신이 없어 기록만(사용자). 혹시 나누게 되면 저장 창이 폴더 선택 창이 된다. 기획서 `원본 데이터 묶음 다운로드` 왜 1 · 와이어프레임 ⑦ 정해야 할 것.
